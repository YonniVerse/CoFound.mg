# Audit des Vagues 1, 2 et 3 — CoFound.mg

**Date de l’audit** : 22 août 2026
**Branche vérifiée** : `dev`
**Référence du backlog** : [`docs/plan-de-developpement.md`](https://github.com/YonniVerse/CoFound.mg/blob/dev/docs/plan-de-developpement.md)

## Conclusion exécutive

Les Vagues 1, 2 et 3 sont **fonctionnellement largement intégrées dans `dev`** et aucune PR ouverte ne concerne actuellement ces trois vagues. La Vague 1 comporte toutefois deux tickets dont la traçabilité n’est pas portée par une PR dédiée : E-05 est indiqué comme intégré indirectement dans E-06, et E-09 est couvert dans la chaîne d’activation sans livraison dédiée clairement identifiable. La Vague 2 est entièrement représentée par des PR fusionnées, plusieurs tickets ayant été regroupés dans une même livraison. La Vague 3 est également intégrée dans `dev`, mais P-03 et P-04 ont des PR fermées sans fusion et P-01/P-05/P-10 ont été regroupés dans d’autres livraisons ou dans la clôture de vague.

> **Distinction importante :** « intégré dans `dev` » signifie que le code et les surfaces fonctionnelles sont présents dans la branche actuelle. Cela ne signifie pas nécessairement qu’un ticket possède sa propre PR fusionnée ni que chaque parcours a été démontré sur une base de recette réelle.

## 1. Validation technique de l’état actuel

Les contrôles lancés sur `dev` sont verts. Le typecheck récursif a réussi pour `packages/shared`, `apps/api` et `apps/web`. La suite de tests API a exécuté **149 tests, tous réussis**, sans échec, annulation ni test ignoré. Le lint récursif a également réussi. Les builds shared et web vérifiés après les changements de finition sont réussis.

| Contrôle | Résultat | Portée |
|---|---:|---|
| Typecheck récursif | Réussi | Shared, API et web |
| Tests API | **149/149** | Unitaires et HTTP disponibles dans le dépôt |
| Lint récursif | Réussi | Workspace |
| Build shared | Réussi | `@cofound/shared` |
| Build web | Réussi | Vite, chunks lazy inclus |
| Workspace | Propre | `dev` alignée sur `origin/dev` au moment du contrôle |

Ces contrôles vérifient la cohérence technique actuelle, mais ils ne remplacent pas une recette complète avec Neon et comptes authentifiés pour les parcours dépendant de données externes.

## 5. Incohérences et risques résiduels

| Sujet | Constat | Action recommandée |
|---|---|---|
| Tickets regroupés | E-05, E-09, M-16 et plusieurs P-* n’ont pas de PR autonome | Ajouter une note de clôture ou une table de traçabilité sans réécrire le backlog officiel |
| PR fermées | P-03/#46 et P-04/#47 sont fermées sans fusion | Vérifier les critères fonctionnels en recette et relier explicitement le code de remplacement |
| Tests locaux | 149 tests API, typecheck et lint verts | Compléter par une démonstration verticale sur staging |
| Données réelles | Aucun audit ne doit utiliser de données personnelles réelles | Utiliser exclusivement le seed `demo-` et une base Neon de recette |
| Permissions | La présence de routes ne prouve pas toutes les interdictions RBAC | Rejouer les tests négatifs sur l’environnement de recette |
| E2E | S-09 n’est pas encore exécuté avec comptes/jeton réels | Fournir les variables `E2E_*`, puis exécuter les trois parcours |

## 6. Traitement des incohérences et risques

La dette de traçabilité a été traitée par la création de [`docs/traceabilite-vagues-1-2-3.md`](traceabilite-vagues-1-2-3.md). Ce document ne modifie pas le backlog officiel ; il explicite les PR regroupées, les tickets sans PR autonome et les PR fermées sans fusion.

E-05 est désormais marqué comme regroupé dans la chaîne mapping/prévisualisation. E-09 est marqué comme présence fonctionnelle à confirmer en recette : le schéma Prisma contient `InvitationToken.tokenHash` unique et `expiresAt`, tandis que le service d’authentification hache le token avant recherche et refuse un token utilisé, expiré ou associé à un compte non invité. Il reste recommandé d’ajouter une démonstration recette du cas nominal, de l’expiration et de la réutilisation.

M-09 à M-11, M-12/M-13 et M-15/M-16 sont explicitement reliés à leurs PR regroupées. P-03 et P-04 restent correctement signalés comme PR fermées sans fusion ; leur présence dans le code ne vaut pas preuve de livraison historique autonome. P-01, P-05, P-10 et P-13 sont documentés comme regroupés.

Le risque RBAC est couvert localement par `apps/api/test/rbac.test.ts`, qui contient sept cas négatifs F-19 ainsi que les contrôles de rôles staff S-05. La suite globale a passé 149 tests API, le typecheck et le lint. Le risque restant est opérationnel : la recette staging, les comptes pseudonymisés et les parcours E2E doivent encore être exécutés.

## 7. Conclusion opérationnelle

Sur la base du backlog et de l’état Git contrôlé, les trois vagues sont **fusionnées fonctionnellement dans `dev`**. La Vague 1 est terminée avec une dette de traçabilité sur E-05 et E-09. La Vague 2 est terminée avec des tickets regroupés dans les PR #55, #66 et #67. La Vague 3 est terminée dans `dev`, mais P-03 et P-04 doivent rester signalés comme PR fermées sans fusion, et plusieurs tickets ont été regroupés.

La prochaine action recommandée n’est pas de recréer artificiellement des PR historiques. Il faut plutôt réaliser une démonstration verticale sur staging, valider les permissions négatives, puis compléter la matrice de traçabilité dans un document d’audit ou de handoff sans modifier le backlog officiel.
